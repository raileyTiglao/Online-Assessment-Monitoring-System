## 0. Prerequisite (already done)

`monitoring/pose_log.py` was added — a per-frame CSV logger, off by
default. To turn it on for a recording session:

1. Open `config.py`, find `OutputConfig`, set:
   ```python
   ENABLE_CONTINUOUS_POSE_LOG = True
   ```
2. Run `main.py` as normal (`py -3.11 main.py`).
3. When the session ends, `pose_log.csv` is written to the project root
   (one row per frame: elapsed seconds, raw and baseline-normalized
   yaw/pitch/roll, per-axis suspicious flags, gaze data, device
   detection, and the risk level classified that frame).

**Important — rename the CSV after every session.** `POSE_LOG_FILE` is a
fixed filename (`pose_log.csv`), so running a second session overwrites
the first one's data. After each session ends:

```
pose_log.csv          → rename to →  pose_log_session01_baseline.csv
session_report.json   → rename to →  session_report01_baseline.json
```

(or move them into a dedicated folder, e.g. `evaluation_sessions/`,
right after each run — do this before starting the next session, not
at the end of all ten).

## 1. The 10 scripted sessions

**For the full minute-by-minute protocol** — exact hold durations tied
to the real thresholds in `config.py`, expected risk-level readout at
each step, and deliberate negative controls — see
`docs/SCRIPTED_SESSIONS.md`. The summary below is just the quick
reference; use the other file when actually recording.

Each session: run `main.py`, complete calibration (~7 seconds, sit
naturally, press SPACE when ready), then perform the scripted behavior
below for roughly 2–5 minutes. Jot down a rough start time (in elapsed
seconds, or just a stopwatch note) whenever the behavior changes within
a session — this is the manual "ground truth" you'll compare the
system's output against afterward, since live in-session labeling isn't
wired up.

| # | Session | Script | What it tests |
|---|---------|--------|----------------|
| 1 | Baseline | Sit normally for the full duration, no suspicious behavior at all. Look at the screen as if reading/typing. | False-positive rate — the system should classify this as LOW the whole time |
| 2 | Downward gaze/pitch | Look down at desk/notes repeatedly, holding each glance for several seconds. | `pitch_suspicious` threshold |
| 3 | Lateral head turns | Turn head left and right repeatedly, holding each turn briefly. | `yaw_suspicious` threshold |
| 4 | Head tilt | Tilt head sideways (ear toward shoulder), hold, repeat. | `roll_suspicious` threshold |
| 5 | Gaze shift only | Keep head still, move only your eyes off-screen repeatedly. | `gaze_suspicious` threshold, isolated from head movement |
| 6 | Tracking dropout | Move out of frame briefly, or occlude your face with a hand, several times. | `dropout_suspicious` |
| 7 | Repeated brief movements | Many short, quick movements (any axis), each too brief to cross the sustained-window threshold on its own. | `RepetitionAnalyzer` — episode counting over a longer span |
| 8 | Device visible only | Hold a phone in frame, pose stays normal throughout. | Object detection module in isolation |
| 9 | Combined device + pose | Hold a phone in frame while also performing a suspicious pose (e.g., downward gaze). | Dual-modal HIGH-risk trigger path |
| 10 | Edge case | Increase distance from camera and/or dim the lighting, then repeat a simple suspicious behavior (e.g., downward gaze). | Matches what's already claimed in Limitations about degraded performance under poor lighting/distance |

**If time is tight, cut in this order:** 10 → 7 → 4. Sessions 1, 2, 3, 5,
6, 8, 9 cover the core signal paths and dual-modal logic most directly
tied to what the paper already claims; those are the ones worth
protecting first.

## 2. After each session

1. Rename/move `pose_log.csv` and `session_report.json` (see step 0).
2. Write down, next to your elapsed-time notes, which risk level you
   *expected* the system to show during each behavior segment (LOW during
   baseline stretches, MODERATE/HIGH during the scripted suspicious
   stretches) — this becomes your ground-truth label column.

---

## 3. Analysis (after all sessions are recorded)

For each session's CSV, in pandas (or Excel/Sheets if preferred):

1. **Descriptive statistics** — mean, std dev, min/max of `yaw`, `pitch`,
   `roll` columns, overall and per scripted segment (using your manual
   timestamp notes to slice the rows).
2. **Threshold accuracy** — for each row, compare the system's
   `*_suspicious` flag (or `risk_level`) against your ground-truth label
   for that row's time range. Compute the proportion that match
   (accuracy), and optionally precision/recall for "suspicious" the way
   Data Analysis already does for the object detector.
3. **Risk classification accuracy** — same comparison but against
   `risk_level` specifically (LOW/MODERATE/HIGH) vs. your expected level
   per segment. A confusion matrix (expected vs. actual) is the natural
   output here.
